Guia de Sobrevivência: Docker Nativo

Bypass de WSL corrompido via Hyper-V

Por que esta arquitetura é necessária?

Este documento detalha o procedimento de "resgate" e configuração de um ambiente de desenvolvimento isolado. Ele é necessário quando o host Windows apresenta corrupção severa no banco de dados de componentes (erro 1603, DISM travado) ou perda de referências de caminho do WSL, inviabilizando a instalação do Docker Desktop tradicional.

⚠️ Sintoma 1: Falha do WSL

O Windows perde o link simbólico do executável do WSL, retornando "caminho não encontrado" mesmo após tentativas manuais de instalação via pacotes .msixbundle.

PS C:\WINDOWS\system32> wsl --install --manual
O sistema não pode encontrar o caminho especificado.
PS C:\Users\Usuario\Downloads> Add-AppxPackage -Path ".\Microsoft.WSL...msixbundle"
>>
>> cd..

✅ A Solução: Isolamento via Hyper-V

Em vez de depender da Microsoft Store ou do WSL (que interagem profundamente com o registro do Windows), isolamos o ambiente subindo o motor Docker nativamente em uma Máquina Virtual Linux gerida pelo Hyper-V, acessando-a via SSH.
